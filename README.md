# MTR Optimization Addon (Fabric 1.19.4)

Клиентский аддон для **Minecraft Transit Railway 4.0.5** (Minecraft 1.19.4, Fabric).
Переносит в MTR 4 те идеи оптимизации из мода MTR-34, которые имеют смысл в архитектуре MTR 4.

## Что делает (v1.5.2)

Все хуки проверены по байт-коду MTR 4.0.5 (1.19.4 Fabric), подробности в `docs/OPTIMIZATION_REPORT.md`.

### Исправления утечек и лагов (главное)

| Параметр (`config/mtr_opt.json`) | По умолчанию | Что делает |
|---|---|---|
| `fixResourceLeaks` | true | `CachedResource` в MTR добавляет каждый ресурс в статический список, откуда ничего никогда не удаляется. Цепочка кэша вагона создаёт новые дочерние ресурсы при каждой пересборке, и все старые остаются навсегда вместе с сырыми данными моделей. Аддон хранит ресурсы слабыми ссылками, чистит статический список каждый тик и освобождает старые модели при `CustomResourceLoader.reload()` |
| `releaseGpuBuffers` | true | В MTR `OptimizedModel.close()` нигде не вызывается, а `VertexArray.close()` удаляет только VAO: буферы вершин и индексов остаются в видеопамяти навсегда. Аддон освобождает VAO, VBO и IBO, когда MTR сбрасывает модель из кэша (с задержкой 1-2 тика, чтобы не задеть текущий кадр) |
| `modelBuildBudgetMillis` | 6 | MTR собирает не больше одного ресурса за тик, а на вагон нужно 7+ сборок подряд (3 уровня цепочки и 4 модели), поэтому поезд при въезде в поле зрения собирается по частям с рывками. Пока потрачено меньше бюджета, разрешается ещё одна сборка. 0 = как в MTR |
| `prewarmVehicles` | true | Модель вагона в MTR собирается только когда вагон первый раз попал в кадр, отсюда лаг при въезде. Аддон собирает модели поездов из списка клиента заранее (тем же вызовом, что рендер), растянув по тикам. `prewarmIntervalTicks` (10) задаёт частоту просмотра списка |
| `vehicleModelCacheMillis` | 120000 | Минимальное время хранения цепочки кэша вагона и его GPU-моделей (в MTR 60000 мс). Поезд, который уже собирали, не пересобирается при каждом возвращении в поле зрения. Память не растёт бесконтрольно, потому что по истечении срока буферы теперь реально освобождаются. Сырые модели из json живут как в MTR. 0 = как в MTR |

### Защита от падений

Любое исключение из кода аддона внутри хуков MTR ловится: в лог пишется одна строка «Ошибка в хуке ...», все исправления кэша
отключаются до перезапуска, а MTR продолжает работать по своей оригинальной логике.

### Остальные настройки

| Параметр | По умолчанию | Что меняет |
|---|---|---|
| `maxRailRenderDistanceBlocks` | 128 | Потолок дальности отрисовки рельсов (`RenderRails.renderWithinRenderDistance`). Дальние рельсы пропадают: компромисс между FPS и картинкой. 0 = как в MTR |
| `maxOcclusionRadiusChunks` | 0 | Радиус occlusion culling в рабочем потоке (в MTR зашито 32). По умолчанию выключено: за пределами радиуса объекты, скорее всего, не отсекаются, и FPS может упасть |
| `workerThreadSleepMillis` | 0 | Пауза рабочего потока culling (в MTR 10 мс). 0 = как в MTR |
| `nodeCheckRadiusBlocks` | 6 | Радиус проверки «висящих» узлов при предмете рельсов в руке. В MTR 16 (35 937 вызовов `getBlockState` за кадр); при 6 их 2 197 |
| `dynamicTextureLifetimeMillis` | 0 | Время жизни динамических текстур (названия станций, знаки, табло). В MTR 10000 мс. В v1.4.0 этот хук не срабатывал: константа в байт-коде `long`, а не `int`. Теперь работает. Малые значения дают мигание знаков при повороте головы |
| `fastStringFormat` | true | Быстрая замена `String.format` в `DynamicTextureCache`, `RenderPSDAPGDoor`, `RenderPIDS`, `RenderLiftPanel` (только `%s`, остальные шаблоны идут в настоящий `String.format`) |
| `resourceTextCacheMaxEntries` | 0 | Ограничение `CustomResourceLoader.RESOURCE_CACHE`. По умолчанию выключено: при пересборке моделей тексты читались бы с диска заново, а это лаг. Для экономии RAM ставьте 512 |
| `statsLogIntervalSeconds` | 0 | Раз в сколько секунд писать в лог статистику аддона: число кэшированных ресурсов, освобождённых моделей и буферов, время сборки моделей, занятая память Java. Поставьте 30, чтобы снять цифры до и после |
| `arrivalsRefreshMillis` | 0 | Период запросов прибытия поездов для табло. В MTR 3000 мс |

## Готовые профили

Меняйте значения в `config/mtr_opt.json` (после правки нужен перезапуск игры).

| Профиль | maxRail | modelCache | modelBuildBudget | textCache | textureLifetime |
|---|---|---|---|---|---|
| По умолчанию | 128 | 120000 | 6 | 0 | 0 |
| Слабый ПК / меньше RAM | 96 | 60000 | 4 | 512 | 0 |
| Много RAM, максимум плавности | 160 | 300000 | 8 | 0 | 0 |

## Что ещё помогает (настройки самого MTR и Java)

- В настройках MTR: «скрывать полупрозрачные части» (`hideTranslucentParts`) уменьшает нагрузку на рендер; «разрешение динамических текстур» (`dynamicTextureResolution`) держите на минимуме, он задаёт потолок размера текстур знаков и табло (2048 * 2^значение).
- Не выделяйте Java лишнюю память: большой `-Xmx` увеличивает паузы сборщика. Для клиента с MTR обычно хватает 4-6 ГБ. Пример аргументов: `-XX:+UseG1GC -XX:MaxGCPauseMillis=50`.

Каждый хук при первом срабатывании пишет в лог строку «Хук активен: ...»: по ней видно, какие миксины применились в вашей сборке MTR.

Конфиг создаётся при первом запуске клиента.

## Сборка

Нужен JDK 17.

```
./gradlew build
```

Готовый jar: `build/libs/mtr-opt-<версия>+mc1.19.4.jar`.
Кладётся в `mods/` вместе с Fabric API и MTR 4.0.5 для 1.19.4.

## GitHub

1. Создайте репозиторий и запушьте папку целиком.
2. Workflow `.github/workflows/build.yml` соберёт мод на каждый push и приложит jar как artifact.
3. Тег `v1.0.0` (`git tag v1.0.0 && git push --tags`) создаёт GitHub Release с jar.

## Важно

MTR как зависимость компиляции **не подключается**: миксины нацелены на классы MTR по строковому
имени (`@Pseudo`) и с `require = 0`. Если в вашей сборке MTR метод или константа отличаются,
конкретный миксин просто не применится, игра не упадёт (смотрите лог `mtr_opt`).

Подробности и список того, что не переносится и почему: [docs/PORTING_REPORT.md](docs/PORTING_REPORT.md).
